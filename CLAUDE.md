# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Wall Run — a tiny browser game (vanilla HTML/CSS/JS, no build step, no framework, no dependencies). First-person/mid-back POV, not a horizontal side-scroller: the runner is a fixed shape anchored near the bottom of the canvas (it never auto-advances) and the wall is a fixed-position rectangle near the top that grows larger — closer, filling more of the screen — as you approach, on an otherwise blank canvas (deliberately no ground/road/horizon, and no on-screen control hints, no border around the game frame). The run ends once the wall's rendered width crosses `IMPACT_TRIGGER_WIDTH_FRACTION` (0.85) of the canvas — large and dominant, but with a sliver of background still visible around it, not fully edge-to-edge. Hold the Up Arrow key (or click/tap the canvas) to sprint and build speed, closing the distance to the wall; Down Arrow reverses (negative speed, undoing progress and shrinking the wall back down); there's no floor at the start line either — you can walk backward from the very beginning of a run for a longer running start, and the wall keeps shrinking smaller than its normal starting size the further back you go (down to a small visible floor, never past disappearing); Left/Right Arrow strafe the runner left/right on screen without affecting that distance. The game has four screens, all drawn on the one canvas (there is no HTML UI at all): a start screen (a `START` graphic), gameplay (wall, runner, and a live speed readout top-right), a brief `'impact'` flash right at the moment of collision (the frozen gameplay frame, wall large but not fully edge-to-edge, with a comic-book explosion burst and a randomly-picked word — `BAM`/`POW`/`WOAH`/`YIKES`/`NO GOOD` — stamped over it), and then a results screen (`TOP SPEED` + a big readout + a `PLAY AGAIN` graphic). A run only ever begins by clicking directly on the `START`/`PLAY AGAIN` graphic — holding Up or clicking elsewhere on the canvas does nothing while a screen other than gameplay is showing. During gameplay there's also an on-screen D-pad on the right side of the canvas (touch/click), mirroring the four arrow keys, with proper multi-touch (e.g. sprint + nudge with two fingers at once). The goal is to reach the highest speed possible at impact. The distance to the wall is randomized each run, and so is the achievable top speed itself (`state.accelScale` — see `update()`), so the same "hold Up the whole time" strategy caps out differently from one play to the next.

## Commands

There is no build, lint, or test tooling in this repo. To run the game locally:

```bash
npm start
```

(`npm start` / `npm run dev` both run `node server.js`, per [package.json](package.json).) Then open http://localhost:8000. The game itself is still plain static HTML/JS/CSS with no build step — [server.js](server.js) exists only so there's a Node process to deploy (see below), and the game can still just be opened directly via `index.html` with no server at all for quick local edits.

## Deploying

[server.js](server.js) is a small dependency-free static file server (built-in `http`/`fs`/`path` only) that binds to `process.env.PORT` (falling back to 8000 locally) — this is what makes the app deployable as a plain Node service, e.g. on Railway: it detects [package.json](package.json), runs `npm start`, and the app binds to whatever port it's given automatically, no extra config needed. It resolves request paths against `__dirname` and rejects (403) anything that `path.normalize`s outside of it, decoding the URL first (so `assets/top%20speed.png`-style paths work) — if you ever touch this file, re-verify that check with a request path containing raw `..`/`%2e%2e` segments rather than trusting a quick curl test, since curl silently normalizes `../` client-side before it ever reaches the server and will make a real bypass look identical to a blocked one; a raw `http.request()` (or any client that doesn't pre-normalize) is what actually exercises the server's own check.

## Architecture

Four files (plus [assets/](assets)), no modules/bundler:

- [server.js](server.js) — deploy-only static file server (see Commands above); has nothing to do with the game's own logic, which is entirely client-side in [game.js](game.js).
- [index.html](index.html) — page shell: nothing but the `<canvas id="gameCanvas">`. There is no HTML UI at all (no buttons, no hints) — every screen (start, gameplay, results) and every readout is drawn onto `gameCanvas` itself by [game.js](game.js), which is loaded as a plain `<script>`.
- [style.css](style.css) — all visual styling, driven by CSS custom properties defined on `:root` in [style.css](style.css). The page is fullscreen/responsive, not a fixed-size centered card: `html, body` are pinned to the viewport (`height: 100%`/`100vh`, `overflow: hidden`, no scrolling), and `.game-shell`'s `width`/`height` are each `min(100vw, ...)`/`min(100vh, ...)` computed from the other dimension via the canvas's fixed 16:9 ratio (960/540, from `index.html`'s `<canvas>` `width`/`height` attributes) — so it always fills the viewport in the binding dimension and letterboxes (centered, via `body`'s `place-items: center`) in the other, at any window size or aspect ratio, without stretching. `#gameCanvas` itself is `width: 100%; height: 100%` of `.game-shell`, so this is purely a CSS/layout concern — the canvas's internal drawing resolution (and everything in [game.js](game.js) that reads `canvas.width`/`canvas.height`, including pointer-coordinate mapping via `getCanvasPoint()`) never changes.
- [assets/](assets) — every piece of art in the game is a hand-drawn, transparent-background PNG here, matching `design1.png`/`design3.png`: `wall.png`, `sprite.png`, digit glyphs `0.png`–`9.png` plus `mph.png` for the speed readouts, `start.png`/`top speed.png`/`play again.png` (note the literal spaces in two of the filenames — `game.js` loads them via `assets/top%20speed.png`/`assets/play%20again.png`) for the start/results screens, `up.png`/`down.png`/`left.png`/`right.png` — solid black arrow glyphs (not sketch-style like the rest, deliberately simpler/cleaner since they're functional touch buttons) for the on-screen D-pad, and `explosion.png` (an outline-only starburst with a transparent interior and no vector path data — `buildExplosionMask()` flood-fills it into a solid white silhouette once, on load, so it actually covers the wall/sprite behind it rather than just outlining over them) plus the impact-word glyphs `bam.png`/`pow.png`/`woah.png`/`yikes.png`/`no good.png` for the impact-flash screen. None of this is drawn with hand-coded canvas paths or in-canvas text.
- [game.js](game.js) — the entire game: state, physics/update loop, and canvas rendering all live in this one file (no classes, just top-level functions and a mutable `state`/`track` object). Key parts:
  - `EXPLICIT_CROPS` / `getCrop(img, key)` (top of file) — most assets have already been cropped tight to their ink and are drawn at full natural size; a couple (currently `wall.png` and `0.png`) still ship with a lot of transparent export margin and need an explicit `{sx, sy, sw, sh}` source rectangle to trim that padding. `getCrop()` is the single lookup every draw call goes through, so if an asset gets re-exported (cropped tight, or padded again), fixing it is a one-line change to `EXPLICIT_CROPS` rather than hunting through draw functions — re-derive the numbers via a quick canvas `getImageData` alpha scan rather than guessing.
  - `wallImage`/`spriteImage`/`topSpeedImage`/`playAgainImage`/`startImage`/`explosionImage`/`impactWordImages` and `digitImages` (top of file) — `Image()` objects loaded from `assets/`. `digitImages` holds `'0'`–`'9'` and `'mph'`; `impactWordImages` holds `bam`/`pow`/`woah`/`yikes`/`'no-good'` (that last key has no space so it works as both an object key and a `getCrop()` lookup, unlike the `no good.png` filename it's loaded from). None of these have load-complete gating beyond the per-draw `image.complete` checks, since `render()` runs every frame anyway and an image just starts appearing on the first frame after it finishes loading.
  - `drawImageFit(img, key, targetWidth, centerX, topY)` / `drawImageCentered(img, key, targetWidth, centerX, centerY)` — draw a whole label-style image at a given width, height derived from its own crop's aspect ratio; `drawImageFit` anchors by its top edge (used by the start/results screens, stacking content top-down), `drawImageCentered` anchors by its center point (used by the impact screen, where the explosion and the word are both centered on the same point). These are the counterparts to the digit-sequence helpers below.
  - `activeButtonRect` / `getCanvasPoint()` / `pointInRect()` — `drawStartScreen()` and `drawResultsScreen()` each set `activeButtonRect` to the on-screen bounding box of their clickable graphic (`startImage`/`playAgainImage`) every time they draw it, in canvas-internal coordinates. `getCanvasPoint()` converts a pointer event's `clientX/clientY` into that same coordinate space (accounting for the canvas's CSS `width:100%` scaling via `getBoundingClientRect()`), and the canvas `pointerdown` handler uses `pointInRect()` against `activeButtonRect` to decide whether a click actually lands on the button — clicking anywhere else on the canvas while not running does nothing. There's deliberately no separate hit-region bookkeeping per screen; whichever screen last drew is the one whose rect is live, and `!state.running` is only true on the start/results screens anyway.
  - `CONTROL_RECTS` / `getControlAt()` / `setControlActive()` / `drawControlButton()` / `drawControls()` — the on-screen D-pad (mobile/touch controls), a plus-shaped cluster of four square buttons on the right side of the canvas (`PAD_*` constants lay out the 3x3 grid it sits in; only the up/left/right/down cells are used, the center and corners are empty). `getControlAt(point)` hit-tests a canvas-space point against all four rects; `setControlActive(control, bool)` is the single place that maps a control key to the actual `state.holdInput`/`reverseInput`/`nudgeLeft`/`nudgeRight` flag it drives — the same flags the keyboard handlers set, so gameplay code never needs to know whether an input came from a key or a touch. `drawControlButton()` renders each button inverted (solid black fill, arrow icon knocked out via `globalCompositeOperation = 'destination-out'`) when its control is currently active, so a touch user gets visual press feedback; this is drawn only during the gameplay screen (`render()`'s `drawControls()` call), never on start/results.
  - `digitSequenceWidth()` / `drawDigitSequence()` — the shared low-level helpers: given a list of glyph keys (digits plus `'mph'`) and a target `glyphHeight`, they measure/draw that row of glyph images left-to-right, each individually scaled by its own crop's aspect ratio so mixed strokes don't distort. `drawSpeedHud()` (live speed, top-right, during gameplay) and `drawResultsScreen()` (the big post-run readout) both build their glyph-key list from a value and call these — there is no text-based speed readout anywhere.
  - `track` (top of file) — fixed layout constants: `groundY` (bottom-anchor for the runner, derived from `canvas.height` so it sits right at the bottom), `distMin`/`distMax` (range `state.startDistance` is randomized from each run), and `wallTopY` (the wall's top edge, pinned in place — it never moves, only grows downward from here).
  - `WALL_ASPECT`/`WALL_START_WIDTH`/`WALL_IMPACT_WIDTH`/`IMPACT_TRIGGER_WIDTH_FRACTION` (top of file) — `WALL_START_WIDTH` (90) is how wide the wall is at the start of a run. `WALL_IMPACT_WIDTH` (`canvas.width + 20`) is the width at `rawProgress === 1` — but a run no longer actually reaches `rawProgress === 1`; it only still matters as the growth curve's asymptote (see `getWallRect()`). The real end condition is `IMPACT_TRIGGER_WIDTH_FRACTION` (0.85, in `update()`): the run ends as soon as the wall's rendered width crosses that fraction of `canvas.width`, which happens well before it reaches `WALL_IMPACT_WIDTH` — impact lands with the wall large and dominant but not fully edge-to-edge (a deliberate visual choice, not a bug — don't "fix" it back to waiting for full coverage).
  - `getWallProgress()` / `getWallRect()` — `getWallProgress()` is the raw, linear, **unclamped** `state.traveled / state.startDistance` (0 at the start of a run, negative while walked backward past the start; in practice it never reaches 1 anymore, see `IMPACT_TRIGGER_WIDTH_FRACTION` above). `getWallRect()` branches on the sign: for `rawProgress > 0`, `forwardEased` raises `min(rawProgress, 1)` to `WALL_GROWTH_EXPONENT` (2.5) — an ease-in curve (0 and 1 map to themselves, but the wall barely grows through the first half of a run and balloons in the back half) — and width interpolates from `WALL_START_WIDTH` toward `WALL_IMPACT_WIDTH` over that. For `rawProgress <= 0`, width instead shrinks *below* `WALL_START_WIDTH` as `1 + rawProgress`, clamped at `WALL_MIN_SHRINK_SCALE` (0.15) so it never quite reaches zero — the two branches agree exactly at `rawProgress === 0` (both give `WALL_START_WIDTH`), so there's no visible jump when you cross the start line either direction. If any of this ever needs retuning, sample `getWallRect().width` at a few `state.traveled` values (forward and negative) rather than eyeballing it — the curve is easy to get wrong by feel alone. Height always follows from `WALL_ASPECT`, centered horizontally with its top pinned at `track.wallTopY`, then adds a parallax `offset` (`-state.lateralX * WALL_PARALLAX_FACTOR * forwardEased` — opposite the strafe direction, zero while shrinking backward, growing with `forwardEased` so it's barely perceptible early and strong right before impact, since it reads as "the camera panning while strafing" rather than the wall itself moving). `drawWall()` is its only caller. Because this only ever produces an axis-aligned `dx,dy,width,height` rectangle — no rotation or shear — the wall stays a plain right-angled box at every size. The parallax offset is clamped to `±overscan` (`(width - canvas.width) / 2`) whenever that's non-negative, so a hard strafe couldn't pull an edge in and expose a sliver of white *if* the wall ever actually reached full-canvas width — at the current `IMPACT_TRIGGER_WIDTH_FRACTION` (0.85) the run always ends before `overscan` turns non-negative, so this clamp branch is currently dormant in normal play, not dead code to delete — it's there for whenever `IMPACT_TRIGGER_WIDTH_FRACTION` (or the parallax factor) gets pushed back up near 1.
  - `state` — mutable run state. `state.screen` is `'start'`, `'gameplay'`, `'impact'`, or `'results'` and is what `render()` branches on (starts at `'start'`). The forward axis is `state.traveled` (accumulated distance covered, driven by `state.speed`) against `state.startDistance`; `state.traveled >= state.startDistance` triggers `finishRun()`, which stops the run outright (`state.running = false`) rather than easing to a halt, and moves to `'impact'` (not straight to `'results'`) — it also picks `state.impactWordKey` at random from `IMPACT_WORD_KEYS` and sets `state.impactTimeRemaining` to `IMPACT_SCREEN_DURATION` (0.9s), and clears `activeButtonRect` so a click during the flash can't accidentally hit whatever the results screen last put there. `loop()` counts `impactTimeRemaining` down each frame (this happens outside `update()`, which only runs `state.running`) and flips `state.screen` to `'results'` once it expires — `drawResultsScreen()` then sets a fresh `activeButtonRect` for `PLAY AGAIN` as normal. `state.lateralX` is the runner's left/right screen offset from center — purely cosmetic strafing, set by `state.nudgeLeft`/`state.nudgeRight` (Left/Right Arrow), and does not affect `traveled` or collision. `state.reverseInput` (Down Arrow) is checked first in `update()` and, when true, overrides the sprint acceleration entirely with negative acceleration (`REVERSE_MAX_SPEED` caps how negative `state.speed` can go). `state.accelScale` is randomized per run (`ACCEL_SCALE_MIN`–`ACCEL_SCALE_MAX`, i.e. 0.7–1.3, drawn in `startRun()`) and scales *both* the sprint acceleration and the top-speed clamp together — so a run's achievable top speed genuinely differs each play (not just how long the wall takes to fill the screen), and a low-`accelScale` run isn't just "the same ceiling reached slower."
  - `update(dt)` — physics: there is no idle/baseline acceleration — with neither Up nor Down held, acceleration is 0 and drag alone decays `state.speed` back toward 0, so nothing progresses (speed, `traveled`, wall growth) until the player actually holds Up; a run starting with everything sitting motionless is intentional, not a bug to "fix" back in. If `state.reverseInput`, acceleration is `REVERSE_ACCEL` and `state.speed` is allowed to go negative (clamped at `-REVERSE_MAX_SPEED`) — negative speed decreases `state.traveled`, which shrinks the wall smaller than its start size via `getWallRect()` (same `rawProgress` drives both, see above); `state.traveled` has no floor, so it can go negative (walking backward from the start line, effectively lengthening the run). Without `reverseInput` it's `BASE_SPRINT_ACCEL * state.accelScale` driven by `state.holdInput` (sprint key/pointer held down), clamped at `BASE_MAX_SPEED * state.accelScale`. Either way, `state.speed / DRAG_REFERENCE_SPEED` is the ratio the drag term (`ACTIVE_DRAG` (28) while actively holding Up or Down, `IDLE_DRAG` (160) otherwise) scales against — `ACTIVE_DRAG` is deliberately small relative to the acceleration constants (`BASE_SPRINT_ACCEL` 75, `REVERSE_ACCEL` -58) so both ramp up fast and hit their respective caps (`BASE_MAX_SPEED * state.accelScale` / `-REVERSE_MAX_SPEED`, i.e. ~70/-30) within well under a second; `IDLE_DRAG` is deliberately large so releasing either key decays speed quickly too — the whole point is that input feels immediately responsive in both directions, not gradual. `BASE_MAX_SPEED` (70) is deliberately a realistic-feeling MPH number, not an arcadey one — if it's ever changed again, scale `REVERSE_MAX_SPEED`, `BASE_SPRINT_ACCEL`, `REVERSE_ACCEL`, and `DRAG_REFERENCE_SPEED` by the *same* factor (this is exactly scale-invariant: `d(kv)/dt = k·accel − drag·(kv)/(k·ref)` reduces to `k·dv/dt`) so the ramp-up/decay *timing* doesn't change, only the numbers on screen — `ACTIVE_DRAG`/`IDLE_DRAG` themselves don't need to move, since they multiply an already scale-invariant ratio. `track.distMin`/`distMax` were shrunk in the same change (500–1400 → 60–150) to keep runs quick despite the much lower speed — these two are the actual knobs for "how long does a run take," not `BASE_MAX_SPEED`, since wall growth is driven by the `traveled/startDistance` *ratio*, not absolute speed. (Sample `state.speed`/`state.traveled` a few frames into a driven `update()` loop to verify any retuning, rather than tuning by feel — see the git history for a worked example.) This drives `state.speed`, which feeds `state.traveled`; `nudge` from Left/Right Arrow moves `state.lateralX` at a fixed `NUDGE_SPEED` independent of speed. Ends with the `finishRun()` check once `traveled` reaches `startDistance`. `update()` (and the whole loop) no-ops while `state.running` is false, i.e. on the start/results screens. `drawSpeedHud()` displays `Math.abs(state.speed)` — there's no "-" glyph asset, so negative speed while reversing shows as a plain magnitude, not a signed number.
  - `render()` — branches on `state.screen`: `'start'` draws `drawStartScreen()` alone and returns; `'impact'` draws `drawImpactScreen()` alone and returns — this redraws `drawBackground()`/`drawWall()` (frozen at whatever size it was the instant `finishRun()` fired, since `state.traveled` doesn't change anymore), then stamps the explosion (`explosionMaskCanvas` if `buildExplosionMask()` succeeded — a pixel-accurate flood-filled white silhouette of `explosion.png`, built once on load; otherwise `drawBurstFill()`, an approximate jagged-star polygon fallback for when `getImageData` is blocked, e.g. opened via `file://` instead of served), then the outline `explosionImage` on top of that fill via `drawImageCentered()`, then `impactWordImages[state.impactWordKey]` centered on that same point — so the burst now actually masks the wall/sprite behind it rather than just outlining over them; `'results'` draws `drawResultsScreen()` alone (`topSpeedImage`, a big digit-sequence readout of `state.maxSpeed`, then `playAgainImage`, stacked and centered) and returns; otherwise it draws the gameplay screen — `drawBackground()` (blank white fill, no ground/road/horizon), `drawWall()`, `drawRunner()` (anchored at `track.groundY`, offset only by `state.lateralX`, never auto-advancing), `drawSpeedHud()` (the live current-speed readout, top-right), then `drawControls()` (the D-pad — gameplay-only). There's no speed-line/whoosh effect — that was tried and removed; the wall's own growth is what sells the sense of closing distance.
  - `loop(timestamp)` — the `requestAnimationFrame` game loop; computes `dt` and calls `update` then `render` each frame.
  - Input handlers at the bottom wire keyboard (`ArrowUp`/`ArrowDown`/`ArrowLeft`/`ArrowRight`) to `state.holdInput`/`state.reverseInput`/`state.nudgeLeft`/`state.nudgeRight`. The canvas `pointerdown` handler branches on `state.running`: while not running it only calls `startRun()` if the click/tap hit `activeButtonRect` (the `START`/`PLAY AGAIN` graphic), otherwise it's a no-op — there is no keyboard way to start or restart a run. While running, `activePointerControls` (a `Map<pointerId, controlKey>`) records which D-pad button (if any — `getControlAt()`, falling back to `'up'` for a tap anywhere else on the canvas, preserving the old click-to-sprint behavior) each pointer landed on, and `pointerup`/`pointercancel`/`pointerleave` all route through `releasePointerControl()`, which clears only that pointer's own control. This is what makes multi-touch work correctly — e.g. sprinting with one thumb on the up button while nudging with the other on left/right — since one finger lifting only clears its own flag instead of a single shared `holdInput` boolean getting stomped by whichever finger last moved. `#gameCanvas` has `touch-action: none` in [style.css](style.css) so the browser doesn't intercept multi-touch gestures as scroll/zoom.

`design1.png`, `design2.png`, `design3.png` are reference/mockup sketches (not used by the running game) that everything in [assets/](assets) was drawn to match — check them before changing that art style.
